## Ownership and correctness

- `Assets.character()` prepares one root per loaded GLTF identity. `toon()` clones each geometry once; subsequent SkeletonUtils clones reuse those prepared geometry objects. The cached root is never recolored by Character.apply(). Exact linear base colors are restored from the geometry-keyed map after Object3D cloning, avoiding userData Color serialization quantization. Current assets.ts SHA-256 is `5876cd6ef6af592b66a6898750c59a655dabdf54945e37be5840ac2c9dd277cc`, matching the candidate record.
- Installed SkeletonUtils creates distinct skeleton objects and maps their bones into each cloned hierarchy. Animation mixers, bone maps and face transforms belong to the individual Character. Skeleton inverse matrices remain shared immutable input under the current Three implementation; no inspected character path mutates them. Sharing is therefore geometry/material ownership, not shared moving bones.
- Selected skinned inputs are cloned and colored before transformation/merge. Successful batches own their merged geometry. Source meshes remain hidden and immutable. Non-skinned selections and failed merges instead get tracked private colored copies. Fresh private attributes are uploaded as new resources, so omitting needsUpdate on their initial color fill is not a stale-upload defect.
- Reapply first releases private fallback copies and restores their source geometry, then removes/disposes old batches. Body replacement uncaches the old mixer and disposes the old rig skeletons while deliberately skipping shared geometry. Batches use a source mesh's skeleton, so collecting the remaining source-mesh skeletons after batch removal still covers those rigs. Cached shared materials are not character-owned and are correctly left undisposed.
- Current character.ts SHA-256 is `919551409f8b1032eb55836e536ee4b8eb60a8c29137ef4eaeb84920c7189fcc`, matching the candidate record. Existing `tests-integrated-06.txt` records all five focused tests passing and 122/122 total. Its five tests meaningfully exercise actual production GLBs, shared-source identity, private rendered geometry, reapplication/body changes, a bone-texture disposal event, and actual non-skinned/failed-merge fallback fixtures. The ownership fixture is strongest for feminine simultaneous instances; static signature coverage includes both bodies.

No new terminal Character/Assets disposal API is supplied. The inspected city path creates a bounded resident set lazily and retains those Character instances while hiding them, so this absence is not evidence of a current unbounded leak. Future character destruction or Assets replacement needs an explicit lifecycle that releases private resources and releases templates only when no users remain. The ownership convention is not enforced by immutable types; future code must not mutate or dispose template geometry.

## What the 74 comparisons establish

I independently compared all 74 corresponding JSON signature entries, including case IDs and appearance values: **zero mismatches**. Both records have the same GLB sizes/hashes and population (24: player/preview, 12 village residents, 10 city residents; 13 feminine/11 masculine). Candidate source hashes independently match the current files. The baseline character source was inspected against ac21d2b; I did not regenerate the baseline or independently reconstruct its temporarily relocated importer. That provenance limit remains, including the documented manually corrected source hashes.

The 74 entries are 24 population cases plus 25 probes for each body (default plus 24 variants). Reading the generator and checking saved values confirms coverage of each enumerated hair/top/bottom/shoe/skin/hair-color/eye/face/cloth-color value in each body; the bit pattern exercises accessory combinations. This is **per-option value coverage, not every Cartesian combination**, and the cases need not be unique looks.

The signature checks visible mesh names, all ordinary geometry attribute/index bytes, material specialization fields and local matrices. Those bytes include skin weights/indices and vertex colors, making it strong evidence against accidental selected-geometry/color changes in these cases. It does not hash animated bone poses, bind matrices, ancestor/world matrices, clips/mixer state, shader source/uniform state, attribute metadata or rendered pixels. Its direct `.array` and non-null index assumptions fit the prepared production path, but are not a general interleaved/unindexed asset validator. Updating one character while another retains the same signature proves static output isolation; bone-object identity adds rig-isolation evidence, but the signature alone cannot prove another character's animated pose stayed fixed.

## Geometry accounting

The collector deduplicates actual backing ArrayBuffers by identity, handling ordinary and interleaved attributes and indices. Counting full backing allocations rather than only attribute view lengths is appropriate for retained geometry storage. It includes hidden wardrobe meshes and raw loaded GLTF geometry, and records population accounting before creating the extra probes. Both body templates' geometry is reached through the instantiated population; omitting the cached template roots does not omit an extra geometry allocation in this case because those roots share the same geometry objects.

| Counted backing bytes | Before | Candidate |
|---|---:|---:|
| Wardrobes | 57,317,016 | 4,776,408 |
| Selected batches | 14,294,940 | 14,294,940 |
| Union with raw GLTF geometry | 74,707,280 | 22,166,672 |

Arithmetic independently confirms **52,540,608 bytes saved, about 70.3% of this counted union**. Wardrobe geometry objects fall from 6,912 to 576, exactly 24 × 288 to 2 × 288; 110 selected batches remain unchanged. This supports a real structural reduction for the declared fully instantiated population. Lazy runtime population may be smaller.

These values exclude skeleton/bone/mixer/object storage, textures, GPU/process memory, transient merge allocations and unrelated world memory. The new cached prepared roots themselves retain extra hierarchy/skeleton objects not included in this metric. Thus neither 22.17 MB nor the 52.54 MB saving is a whole-heap result or a direct prediction of browser savings. No arrival-stall cause, FPS improvement, peak/settled memory pass, or post-journey plateau follows from these records.
